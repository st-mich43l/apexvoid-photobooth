# UX-5 library and frame catalogue audit

## Before

The Gallery fetched at most 1,000 media rows and 500 sessions, then filtered and grouped that incomplete window in React. It could not find older sessions and created image components for the whole loaded window. Session trash processed at most 2,000 visible items; an error or crash between file moves and the database update could leave media split between locations. There was no session export or durable session restore. Frames had category and photo-count filters, but no name search, favorites, or operator-controlled guest ordering. Bulk visibility updates stopped on the first error and did not explain which items had changed.

## Changes

* The session-first Gallery asks SQLite for 40 cards at a time with session-ID, mode, status, UTC date, simulated and operator-test filters. Keyset cursors use normalized UTC creation time plus ID, so a new session appearing above the current page does not shift older results. Media within a session uses deterministic 50-item offset pages in capture order; the screen renders only one page at a time. Missing thumbnails have a placeholder. Existing list APIs remain available.
* A session detail exposes media, the existing editor, viewer navigation, original/edited export, composition/print actions, and up to 50 recent print jobs with the existing confirmed reprint action. ZIP session export snapshots media metadata to a private temporary stream (deleted after a normal completion or error), then streams originals (including discarded retakes), compositions, video and optional edited files without holding the session write lock during file copying. It refuses active sessions, unrelated paths and existing names, and cleans up a failed archive. The manifest contains only selected session metadata.
* Active sessions and their media cannot be trashed. A persistent SQLite journal records media and session trash/restore progress. Moves use exclusive same-filesystem hard links followed by unlink, avoiding replacement of an existing file; recovery recognizes an interrupted link/unlink and resumes. A failed operation stays visible as `trashing` and can be restored or retried; completed trashed sessions are available through the status filter. Original media statuses are retained on restore. No fixed media count limits the operation. Empty Trash remains the existing separately confirmed permanent operation.
* Frame search, layout, category, count, source, visibility and favorite filters supplement the existing builder and renderer. Favorites and ordering are atomic catalogue metadata, shared with the guest list. Visibility bulk updates report individual failures and refresh the catalogue; hiding the last offered frame requires confirmation. Frame snapshots are not changed.

## Evidence and limits

The synthetic large-library test inserts 2,001 sessions and 10,005 media rows, pages the full catalogue after inserting a newer session, and checks filtering and page boundaries. On the development Linux environment, the complete test including its inserts took approximately 0.23 s; this is not a hardware benchmark. A separate test moves and restores 2,001 actual synthetic files, and tests cover an interrupted move, partial failure, no-overwrite export and preservation of print history.

Session media pages use offsets, so an actively changing session can shift items between pages; refresh after a capture or edit. The Gallery's print history is explicitly limited to the 50 most recent jobs for a session. ZIP export refuses a missing original instead of silently producing an incomplete archive. The trash filesystem must support same-volume hard links; an unsupported filesystem or a collision stops visibly with the journal retained. The journal supports process-crash replay, but sudden power-loss durability and Windows filesystem behavior have not been physically tested. Multiple independent app processes sharing a library are not coordinated by the in-process lock. The existing startup integrity scan still inspects media records and files; large, slow disks can affect startup.

Screenshots in `docs/img/ux5` were made with the Go UI harness, synthetic sessions and a fake printer. The bulk-error screenshot deliberately injects failed frame updates. Actual Windows WebView2, camera and printer testing remain **UNVERIFIED** unless separately recorded.
