# UX-6 release-readiness audit

Baseline: master at `a087e37` (UX-5 merged). This audit separates software evidence from acceptance on the target kiosk. No physical EOS R50, webcam, printer, or Windows touchscreen was available for this audit. The application is **not production-qualified**.

## P0 — release blockers

* **Canon redistribution permission is unconfirmed.** `.github/workflows/ci.yml` on master builds an executable containing extractable EDSDK DLLs, retains a staging artifact for one day and a final artifact for 30 days. The applicable Canon agreement has not been reviewed or permission documented. Ability to decrypt/use the SDK is not distribution permission. Do not publish or distribute that artifact pending a documented decision; use the standard build with an independently authorized SDK. The existing artifact documentation incorrectly calls the standard artifact the only artifact. Access to existing Actions artifacts should be reviewed by the repository owner. Encrypted vault material and passwords must not enter artifacts or logs.
* **Physical acceptance is UNVERIFIED.** The Canon EOS R50, JPEG/RAW+JPEG/RAW-only behavior, delayed transfer attribution, UVC switching, physical printer, paper dimensions, touchscreen, WebView2 and recovery after power loss require target hardware. `internal/camera/edsdk/reliability_test.go` uses a fake SDK and tests a late event within a configured grace period; it does not prove arbitrary delayed real-camera events cannot be attributed to a later shot. `--canon-validate` is an acceptance tool, not evidence that an R50 passed.
* **Ownership before startup was missing.** On the baseline, `app.New` opens/migrates SQLite and runs recovery before Wails' single-instance enforcement; independent processes also had only process-local session mutexes. This branch adds an OS-backed per-user application lock and per-library lock, including destination ownership during migration. Lock files persist but contain no ownership state; the OS releases locks on process exit. Network filesystems and hostile/non-cooperating processes are not qualified. Cross-process tests exercise contention and process exit; Windows CI must confirm its implementation.
* **Trash recovery failures were not fatal.** Baseline startup logged `Store.Verify` failures and continued. This branch aborts before the UI/media server if recovery fails and releases ownership; an integration test covers a broken journal. No claim is made about durability under actual power loss. Basic same-volume hard-link support is now checked before starting new trash operations. Per-file permissions or nested mounts can still fail after work has started; the journal retains those operations for retry/recovery.

## P1 — must resolve or qualify before release

* Startup performs a synchronous integrity and orphan scan and recovered-video scan; it is safer than exposing unrecovered originals, but scales with media and directories. A synthetic local Linux test created 2,001 sessions and 10,005 media rows referencing small files; startup took about 0.16–0.19 seconds after fixture creation. This is not a Windows, network-share, HDD, antivirus, or cold-cache benchmark. Integrity verification contains best-effort filesystem and database operations; failure handling needs further review. Deferring work safely requires a separate recovery design.
* Shutdown closes capture, recording, camera/SDK, loopback server and SQLite. This branch waits for print polling and preferred-camera startup before releasing resources; physical disconnect, FFmpeg process lifetime, forced termination and repeated WebView2 lifecycle remain UNVERIFIED. Process locks are advisory and cannot protect a library against older application versions or external tools.
* `internal/app/support_api.go` already exports a sanitized text summary, but current daily logs can contain device names and paths, are age-pruned rather than size-bounded, and are not a complete sanitized support bundle. Offline diagnostics, redaction and bounded rotation need qualification.
* WebView2 presence, installation and offline deployment need an explicit prerequisite check and actual Windows testing. Existing CI tests a headless executable, not the Wails window. A Windows installer, signing identity and deployment/upgrade tests are not established.
* Translation resources and Vietnamese UI/font coverage are not established. Existing image captions and prior compositions must not be rewritten when a language changes.
* Same-volume hard links are required for trash. Removable, redirected Documents, OneDrive, long/non-ASCII paths, read-only/low-space cases and network-backed folders need the actual filesystem matrix. A complete backup must include SQLite and media together while the application is shut down; SQLite alone is not a library backup.

## P2 — software evidence and outstanding qualification

* CI run #274 for UX-5 passed Go/frontend tests, Windows portable tests, executable startup self-test and file-port printing. Its Windows log recorded a 157,386-byte PDF beginning `%PDF-`; this demonstrates native spooler/GDI on a software printer, not physical delivery or paper accuracy. Canon-enabled jobs were skipped on that pull request. The camera-free probe and simulated camera are not hardware acceptance.
* Existing tests cover SQLite migrations, session recovery, 2,001-file trash/restore, 10,005-row catalogue pagination, frame composition, capture and print workflows. UVC uses synthetic inputs in automated tests. Screenshots are browser-harness captures, not WebView2 evidence. Consult `docs/UX5_AUDIT.md` and `docs/HARDWARE_TESTS.md` for prior limits.
* The release process needs version/build metadata, reproducibility evidence, complete checksums, release notes, signing instructions, installer/upgrade/uninstall checks and explicit physical acceptance records. CI currently may skip native file-port printing if no suitable driver exists; a release gate must not treat that skip as a physical PASS.
